# 企业餐厅网络点餐系统 - 答辩文档

> 系统简介见 §0，测试演示见 `test_steps.md`，完整设计见 `design.md`。

## 0. 系统简介（30 秒版）

企业内部网络订餐系统：餐厅经理维护**食谱**并从中选菜生成**菜单**，员工每天在**订餐截止时间**（默认 09:00，可配）前从当前菜单下单（每日一单），截止后**厨房主管**按**总括订单**（菜品分量汇总）备料，**配餐开始时间**（默认 11:30，可配）后**配餐员**批量查看订单配送、同时开启次日订餐，月底经理/财务出月度销售统计，员工可查个人消费。

后端 Spring Boot 4.1.1 + MyBatis + MySQL，纯 REST API（前后端分离），Session+Cookie 会话、SHA-256 加盐密码、双拦截器权限、三层快照数据模型，共 13 个模块 47 个接口。

## M1 认证与会话

### 实现介绍

登录/注册/登出/当前用户/修改密码 5 个接口。登录校验通过后把 `LoginUserVO`（**不含密码**）存入 HttpSession，响应自动下发 `JSESSIONID` Cookie；注册为公开接口，角色固定 EMPLOYEE，注册即建立会话；登出 `session.invalidate()`；改密码先校验旧密码。配套 `LoginInterceptor` 拦截 `/api/**`（登录/注册白名单），Session 无用户统一返回 401。

### 可能提问

**Q：Session 是怎么工作的？**
HTTP 无状态，登录成功后服务器把用户信息存入内存中的 HttpSession（Tomcat 维护 sessionId→数据 的 Map），响应头 `Set-Cookie: JSESSIONID=随机ID`；浏览器后续请求自动携带该 Cookie，服务器凭 ID 找到会话识别用户。**数据在服务端、Cookie 只存 ID**，所以安全；登出 invalidate 后旧 ID 立即失效（已实测 401）。

**Q：为什么密码用 SHA-256 加盐，不用 MD5 或 BCrypt？**
MD5 已被证明不安全（碰撞、彩虹表）。SHA-256 单向散列强度更高；加盐（salt+明文再散列）使相同密码密文不同、彩虹表失效。盐存在服务端配置（application-local.yml，经 @ConfigurationProperties 加载，不入库），数据库泄露也难还原。选它而非 BCrypt：JDK 自带 MessageDigest 零依赖、原理易讲透；BCrypt 更安全（自带迭代），可作为改进点。

**Q：为什么不用 JWT？**
课程必做项要求 Session+Cookie；本系统单机内部应用，Session 简单直观、可服务端强制下线。JWT 无状态适合集群，但服务端无法主动失效，与课设场景不匹配。

**Q：注册为什么固定 EMPLOYEE 角色？**
需求规定"用户不需要注册，由管理员添加"；注册是演示入口，若允许自选角色会产生越权风险（任何人注册成经理）。管理员添加指定角色走 M2。

## M2 用户管理

### 实现介绍

用户 CRUD + 重置密码 6 个接口（仅经理）。列表支持姓名/登录名关键字、角色、部门组合筛选 + 手写 LIMIT 分页；新增校验登录名唯一、角色枚举合法，密码 SHA-256 加密入库；修改不含密码；**删除有双重保护**：不能删自己、存在有效订单的用户不可删（避免订单失去归属）；重置密码直接以新密码散列覆盖。

### 可能提问

**Q：删除用户的保护逻辑为什么这么设计？**
不能删自己是防误操作锁死系统；有有效订单不可删是因为订单有员工快照但仍关联 user_id 做统计归属，删掉会导致"员工月度报表"无法溯源。保护规则在 Service 层校验，Controller 只做转发。

**Q：密码重置和修改密码有什么区别？**
修改密码（M1）需旧密码验证，是自己改；重置密码（M2）是管理员直接设新密码，用于员工忘记密码场景。两者最终都走 SHA-256 散列入库。

**Q：角色字段怎么校验？**
入库前 `Role.valueOf(role)` 校验枚举合法性，非法值返回 400"非法的角色值"；权限判定侧（RoleInterceptor）同样以枚举比对，两处都不会因脏数据越权。

规划 `POST /api/files/upload/image`：图片（jpg/jpeg/png/gif/webp，≤5MB）上传至 **MinIO** 对象存储（utils/MinioOssUtil 已封装：建桶 + putObject，对象名 UUID 重命名防冲突），返回访问 URL 存入食谱/菜单 photo 字段。

### 可能提问

**Q：为什么用 MinIO 而不是存本地磁盘？**
MinIO 是 S3 兼容的对象存储：自带 HTTP 访问、独立部署、容量可扩展，图片直接走 URL 访问无需后端静态映射；本地磁盘方案与服务器耦合（扩容、迁移、备份都麻烦）。开发环境单机即可跑 MinIO，成本低。

**Q：上传的安全限制有哪些？**
类型白名单（仅图片后缀）、大小限制（5MB）、UUID 重命名（防路径穿越与覆盖）、MinIO 桶策略控制访问。

## M5 食谱管理

### 实现介绍

食谱（菜品库）CRUD + 批量删除 6 个接口。写操作权限：经理+厨房主管（`@RequireRole`），查看登录即可。列表按名称模糊 + 分类精确筛选、分页。批量删除一次请求删除多个 id（MyBatis `<foreach>` 拼 `IN`）。**删除/修改食谱不影响已有菜单与订单**——快照机制保证（M7 详述）。

### 可能提问

**Q：批量删除怎么实现的？SQL 怎么写？**
请求体 `{ids:[1,2,3]}`，Mapper 用 `<foreach>` 生成 `DELETE FROM recipe WHERE id IN (1,2,3)`，一条语句完成；配合参数化 `#{}` 无注入风险。

**Q：为什么食谱的修改不影响菜单？**
菜单创建时从食谱**复制**菜品信息（快照），此后两边独立。这是需求明确要求（"删除或修改库中菜式不能影响已有菜单或订餐记录"），用复制代替外键关联实现。

## M6 菜单管理

### 实现介绍

菜单列表/当前菜单/创建/详情/删除/启用 6 个接口（写操作仅经理）。菜单有独立名字与状态 USE/HISTORY。**创建即启用**：事务内旧使用中菜单转历史 + 新菜单置 USE + 从食谱快照选菜；`activate` 接口可把历史菜单重新启用（复用）；使用中菜单禁止删除；删除历史菜单时级联删除其菜品。

### 可能提问

**Q：同一时刻只有一份使用中菜单，数据库怎么保证？**
MySQL 无法用唯一索引表达"至多一行 status='USE'"（部分唯一索引不支持），所以由**业务层保证**：所有改变菜单状态的路径（创建、启用）都走同一个事务模板——先把全部 USE 置为 HISTORY，再置目标为 USE。事务隔离下不会出现两份 USE。

**Q：创建菜单和启用菜单有什么区别？**
创建=新菜单+选菜快照+自动启用；启用=把已存在的菜单（通常是历史菜单）重新设为使用中。两者切换逻辑相同，区别是"带菜新建"还是"复用旧菜单"——对应需求"历史菜单留存并可复用"。

## M7 菜单菜品管理

### 实现介绍

向菜单加菜/修改价格/删除菜品 3 个接口（仅经理）。加菜从食谱快照复制（按来源 recipe_id 去重，已存在则跳过）；改价只更新 menu_items 本行，与食谱价格独立；删菜只删菜单项，不影响食谱与已有订单。

### 可能提问

**Q：为什么菜单菜品要复制一份而不是直接引用食谱？**
引用会让菜单价格跟着食谱波动，也无法实现"菜单里单独改价"（需求要求）。复制（快照）后：食谱改价/删除 → 菜单不变；菜单改价 → 食谱不变；下单时再从菜单复制一份 → 订单不随菜单变动。三层各自独立，正是需求"改动互不影响"的实现。

**Q：加菜时重复选同一菜品怎么办？**
Service 层先查该菜单现有菜单项的 recipe_id 集合，与请求的 recipeIds 求差集，只插入新增部分——幂等友好，不会出现重复菜品行。

**Q：改价会追溯影响吗？**
不影响。已下单的订单明细是下单时刻的第三层快照（M8），菜单改价只影响之后的新订单。

## M8 点餐下单（核心）

### 实现介绍

订餐状态/下单/我的订单 3 个接口（所有角色）。**订餐状态**：服务端读系统配置（M13）判定——当前 < 截止时间 → 可订当天；≥ 配餐开始时间 → 可订次日；之间 → 拒单并给原因。**下单**：① 窗口校验并计算用餐日期（前端不传日期，不可信）；② 唯一性预检（user_id+meal_date）；③ 校验菜品属于当前 USE 菜单；④ 快照生成订单明细并算总价；⑤ 事务内插入 orders + 批量插入 order_items。

### 可能提问

**Q：用餐日期为什么由服务端计算而不是前端传？**
前端时间可被篡改（改系统时间就能"提前"订次日的餐）；服务端以自身时钟为准，窗口判定与日期计算一致，杜绝绕过。数据库还有 `(user_id, meal_date)` 唯一约束兜底。

**Q：每日一单怎么保证？**
三层：数据库唯一约束 `uk_user_meal`（兜底）→ 下单前业务预检返回友好 400 → 经理删单为物理删除，删后窗口内可重新下单（员工不会因误删没饭吃）。

**Q：订单为什么要存姓名/电话/工位快照？**
配送信息（电话、工位）若查用户表取实时值，员工离职/改工位后历史订单配送信息就变了；下单时固化快照，保证"当时的配送信息"可追溯，也符合需求"订单包含员工姓名、联系电话"。

**Q：下单的事务边界？**
整个下单方法 `@Transactional`：插入订单主表、批量插入明细任一步失败整体回滚，不会出现"有单无明细"或"有明细无单"。总价在内存用 BigDecimal 算好再落库，避免先插 0 再改。

## M9 订单管理

### 实现介绍

按用餐日期查询（分页，默认取"最近一个可订用餐日期"）/详情/经理删单 3 个接口。详情有归属校验：普通员工只能看自己的订单，经理/配餐员可看任意。删单为**物理删除**订单+明细（事务）。

### 可能提问

**Q：删除订单为什么用物理删除而不是软删除（状态标记）？**
需求原文是"删除员工已经提交的订单"，物理删除字面一致；且 `(user_id, meal_date)` 唯一约束要求被删的订单彻底让位（员工可重订），软删除会与唯一约束冲突。删除的订单自然不再参与统计，符合"已取消订单不参与统计"的口径。

**Q：为什么配餐员也能查全部订单？**
需求：配餐员需按员工批量打印所有订单用于配送（M10），需要查看当日全部订单的权限；但配餐员不能删单、不能看统计。

## M10 总括订单与配餐

### 实现介绍

总括订单（厨房主管备料）：某用餐日期全部有效订单按"菜名+单位"聚合分量（一条 `JOIN + GROUP BY` SQL），附订餐人数；配餐批量（配餐员配送）：当日全部有效订单及明细，按员工列出（姓名/电话/工位/菜品分量），前端据此渲染打印页（浏览器打印，落款送餐员/打印时间）。

### 可能提问

**Q：总括订单的汇总 SQL 思路？**
```sql
SELECT oi.name, oi.unit, SUM(oi.qty) AS totalQty
FROM order_items oi JOIN orders o ON oi.order_id = o.id
WHERE o.status='VALID' AND o.meal_date = ?
GROUP BY oi.name, oi.unit
```
已取消订单被 WHERE 过滤；快照表自带菜名/单位，无需回连菜单表。

**Q：打印功能在后端还是前端？**
前端渲染 + 浏览器打印（window.print），后端只提供结构化数据接口。B/S 架构下浏览器打印最自然，避免后端引入报表模板引擎的复杂度。

## M11 月度销售统计

### 实现介绍

月度销售总报表查询接口（经理/财务；Excel 导出 TODO）。按用餐日期归属月份、有效订单、`GROUP BY 菜名+单位` 聚合：分量=SUM(qty)、金额=SUM(amount)、单价=金额÷分量（加权平均）、总计=金额合计。

### 可能提问

**Q：统计口径里的三个关键点？**
① 按**用餐日期**归月（而非下单时间——月底订次月餐不会串月）；② 已取消订单不计入；③ 同一菜品因菜单改价可能有多个历史单价，所以**单价用加权平均**（金额合计÷分量合计），保证"分量×单价=金额"恒成立。

**Q：为什么统计 SQL 只在 order_items 上做？**
订单明细是下单快照（含菜名/单位/单价/金额），统计直接对快照聚合即可，不需要回连菜单或食谱表——这正是快照设计的收益。

## M12 员工与个人报表

### 实现介绍

员工月度订单汇总（经理/财务查任意员工）、个人月度消费统计（按菜品分组，结构同 M11 但限 user_id）、个人月度订单汇总（自己当月每天订单）3 个查询接口（3 个导出 TODO）。订单列表的明细用 `WHERE order_id IN (...)` 一次批量查出再按 orderId 分组装配，避免逐单查询的 N+1 问题。

### 可能提问

**Q：个人报表和员工报表是什么关系？**
同一套查询逻辑，区别在权限与范围：员工报表由经理/财务指定 userId 查询；个人报表强制取当前登录用户 id（从 Session 取，不接受参数），任何角色都能查自己——对应需求"员工可打印自己的个人月度统计"。

**Q：为什么强调批量装配明细？**
订单列表若每单单独查明细，10 单就是 10+1 次 SQL（N+1）；先查订单、收集 id 集合、`IN` 一次查全部明细、内存分组装配，固定 2 次 SQL。数据量不大但演示了基本优化意识。

## M13 系统配置

### 实现介绍

订餐截止时间/配餐开始时间查询与修改 2 个接口（查询登录即可、修改仅经理）。配置存 system_config 表（key-value），未配置时用默认值 09:00/11:30 兜底；修改时校验 HH:mm 格式与"配餐开始时间必须晚于截止时间"。

### 可能提问

**Q：这些时间为什么放数据库而不是配置文件？**
需求要求"由最终用户自定义"——即运行期可由经理在界面上修改且立即生效。配置文件需要重启才生效，且经理无法操作；数据库 key-value 表天然支持运行期读写。默认值兜底保证建库后未初始化也能正常运行。

**Q：修改配置后多久生效？**
每次订餐状态判定、下单都实时读库（数据量小、频率低，无需缓存），保存后立即生效。校验在保存时做，保证库中配置永远合法。

## 跨模块共性问题

**Q：权限体系一句话总结？**
两个拦截器：LoginInterceptor 保证"已登录"（401），RoleInterceptor 按 `@RequireRole` 注解校验角色（403）；方法不标注解=任何登录用户可用（对应"任何用户都拥有普通员工点餐权限"）；权限矩阵见 test_steps.md T9。

**Q：统一响应体和异常处理？**
全部接口返回 `{code, msg, data}`；业务异常/参数校验/兜底异常由 `@RestControllerAdvice` 统一转换，Controller 零 try-catch；HTTP 状态码与 body.code 同步（401/403/400/500）。

**Q：分页方案？**
`pageNum/pageSize` 约定 + 手写 `LIMIT #{offset}, #{size}` + COUNT 查询，返回 `{total, list}`；参数全部 `#{}` 防注入。

**Q：跨域与 Cookie？**
后端 `allowCredentials(true)` + `allowedOriginPatterns("*")`（携带凭证不能配 allowedOrigins "*"），暴露 Content-Disposition；前端 fetch `credentials: 'include'`。

**Q：还有哪些未完成？**
文件上传/下载（M3/M4 + 报表导出）共 9 个接口为 TODO，已在接口文档标注；密码可升级 BCrypt 或增加 SHA-256 迭代；Session 可迁移 Redis 支撑集群。

**Q：小组分工？**
按 13 模块四大域分工：组员1 用户域（M1-M4）、组员2 菜品域（M5-M7）、组员3 订单域（M8-M10）、组员4 报表域（M11-M13），以接口文档为契约并行开发、逐模块联调。
