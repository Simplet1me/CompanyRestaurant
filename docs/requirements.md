# 企业餐厅网络点餐系统 - 需求分析

## 1. 项目概述

某企业餐厅需要实现一套**内部网络自动订餐系统**（B/S 架构），覆盖从"餐厅备菜 → 员工订餐 → 厨房备料 → 配餐配送 → 月度统计"的完整业务闭环。

典型的一天流程：

1. 餐厅经理维护食谱（菜品种类库）与菜单（当日可点的菜品）；
2. 员工在**订餐截止时间**前登录系统，从菜单选菜下单（每天一张订单）；
3. 截止后**厨房主管**打印**总括订单**（当天所有菜品的分量汇总），据此加工备料；
4. **配餐开始时间**后，**配餐员**按员工批量打印所有订单，据此配送午餐；
5. 配餐开始后员工即可订第二天的餐，直到第二天订餐截止时间；
6. 月底，餐厅经理/财务进行月度销售统计，员工可查看打印个人月度消费。

## 2. 系统角色与权限

系统按**角色**管理权限，共 5 种角色。**任何用户（不论角色）都拥有普通员工的点餐权限**。角色之间是主从职责关系，不互相排斥点餐能力：

| 角色 | 权限说明 |
|---|---|
| 餐厅经理（MANAGER） | 相当于系统管理员，拥有系统最高人事管理权限：用户管理（添加、批量导入）、菜单管理、食谱管理、删除员工已提交订单、统计报表、系统参数配置；同时拥有普通员工权限 |
| 厨房主管（CHEF） | 食谱管理（含批量删除）、打印总括订单（备料）；同时拥有普通员工权限 |
| 配餐员（DELIVERER） | 查看并批量打印当日所有订单（配送）；同时拥有普通员工权限 |
| 财务管理（FINANCE） | 月度销售统计、员工月度订单汇总；同时拥有普通员工权限 |
| 企业员工（EMPLOYEE） | 点餐、查看打印自己的个人月度消费统计汇总表和月度订单汇总表 |

权限矩阵：

| 功能 | 经理 | 厨房主管 | 配餐员 | 财务 | 员工 |
|---|:-:|:-:|:-:|:-:|:-:|
| 登录 | ✓ | ✓ | ✓ | ✓ | ✓ |
| 点餐（普通员工权限） | ✓ | ✓ | ✓ | ✓ | ✓ |
| 用户管理（添加/批量导入） | ✓ | | | | |
| 食谱管理（增删查改/批量删除） | ✓ | ✓ | | | |
| 菜单管理（创建/改价/删除菜品/更换） | ✓ | | | | |
| 删除员工已提交订单 | ✓ | | | | |
| 总括订单（备料汇总） | | ✓ | | | |
| 批量打印订单（配餐） | | | ✓ | | |
| 月度销售统计总报表 | ✓ | | | ✓ | |
| 员工月度订单汇总表 | ✓ | | | ✓ | |
| 个人月度消费统计/订单汇总 | ✓ | ✓ | ✓ | ✓ | ✓ |
| 系统参数配置（订餐时间） | ✓ | | | | |

**用户不需要注册**：由拥有权限的用户（餐厅经理）在后台添加，且支持**批量导入**。（为便于演示，系统另提供自助注册入口，注册用户角色固定为 EMPLOYEE，见 FR-07。）

## 3. 功能需求

### 3.1 认证与用户管理

- FR-01 登录：用户凭登录名 + 密码登录；登录成功后使用 Session 保持登录态（Cookie 承载 JSESSIONID）。
- FR-02 登出：销毁会话。
- FR-03 获取当前登录用户信息。
- FR-04 用户添加/查询/修改/删除（餐厅经理）。
- FR-05 用户批量导入（餐厅经理）：上传 Excel 文件，后端解析并批量创建用户。
- FR-06 用户密码管理：修改密码（自己或管理员重置）。
- FR-07 自助注册（演示入口）：填写姓名、登录名、密码、联系电话、工位信息（部门可选），**角色固定为 EMPLOYEE**，注册成功即建立会话；管理员添加与批量导入途径不变（FR-04/FR-05）。

### 3.2 食谱管理（recipe）

食谱是餐厅的**菜品库**，是菜单的数据来源。

- FR-10 菜品增删查改（餐厅经理、厨房主管）。
- FR-11 **菜品图片上传**：创建或编辑菜品时提供上传图片功能（编程实现文件上传）。
- FR-12 菜品查找：支持按名称/分类检索。
- FR-13 **批量删除**（餐厅经理、厨房主管）。
- FR-14 删除或修改库中的菜式信息**不能影响**已有的点餐单、菜单或订餐记录（→ 快照机制，见 §5.3）。

### 3.3 菜单管理（menu）

餐厅经理从食谱中选出若干菜品（菜肴、点心、主食、糖水等）形成菜单。

- FR-20 创建菜单：每个菜单有**独立的名字**；从食谱中选菜加入菜单（菜品信息含图片、价格、计量单位）。
- FR-21 菜单菜品**修改价格**（不影响食谱原价）。
- FR-22 菜单菜品**删除**。
- FR-23 菜单**持续使用**，直到经理更换新菜单：创建并启用新菜单后，旧菜单自动转为历史。
- FR-24 历史菜单**留存并可复用**（可重新启用历史菜单）。
- FR-25 员工下单时只能看到**当前使用中的菜单**。

### 3.4 订餐（order form）

- FR-30 员工在**订餐窗口**内（见 §5.1）从当前菜单选择菜品、填写分量，生成订单。
- FR-31 **每个员工每天只生成一张订单**（按用餐日期唯一）。
- FR-32 员工可查看自己的订单。
- FR-33 餐厅经理可以**删除员工已经提交的订单**。
- FR-34 菜单菜品信息（菜名/单位/单价）在**下单时以快照固化**到订单，后续改价不影响已有订单。

### 3.5 总括订单与配餐（blanket order）

- FR-40 订餐截止时间后，厨房主管可查看/打印**总括订单**：当天所有订单按菜品（食品）汇总的**分量清单**，用于控制配料加工。
- FR-41 配餐开始时间后，配餐员按员工批量查看/打印当天**所有订单**（含员工姓名、联系电话、工位信息、点餐明细），用于配送午餐。

### 3.6 统计报表

- FR-50 **月度销售统计总报表**（经理、财务）：按统计年月，汇总售出的菜品分量、总金额（按菜品分组的明细 + 总计）。
- FR-51 **员工月度订单汇总表**（经理、财务）：单独列出某位员工每月的所有订餐记录（每天一单）。
- FR-52 **员工个人月度消费统计汇总表**（所有用户均可查自己）：按菜品分组的月度消费明细 + 合计金额。
- FR-53 **员工个人月度订单汇总表**（所有用户均可查自己）：自己每月的订单列表。
- FR-54 报表支持**导出 Excel 文件下载**（编程实现文件下载）。

### 3.7 系统配置

- FR-60 **订餐截止时间**（默认 09:00）：可由最终用户（餐厅经理）自定义。
- FR-61 **配餐开始时间**（默认 11:30）：可由最终用户（餐厅经理）自定义。

## 4. 数据需求

### 4.1 用户（user）

| 字段 | 说明 |
|---|---|
| 姓名 | |
| 登录名 | 唯一，登录凭据 |
| 密码 | 加密存储 |
| 联系电话 | 送餐用 |
| 工作单位（部门） | |
| 工位信息 | 送餐用 |
| 角色 | 见 §2 五种角色 |

### 4.2 食谱（recipe）

| 字段 | 说明 |
|---|---|
| 菜肴名称 | 如：青椒炒肉丝、米饭、西红柿蛋汤 |
| 分类 | 如：主食、糕点、菜肴（例：炒白菜-菜肴、米饭-主食、馒头-主食、银耳汤-甜点） |
| 菜品图片 | 上传图片，存 URL |
| 计量单位 | 如：份、两、个、例、杯 |
| 单位价格 | 数值（元） |

### 4.3 菜单（menu）与菜单菜品（menu_items）

- 菜单：独立名字、创建时间、使用状态（使用中/历史）。
- 菜单菜品：菜品信息与食谱**基本一致**（名称、图片、分类、单位），另有**可独立修改的价格**、所属菜单 id。
- 注意：`数据举例.xlsx` 中 menu_items 未列出 price 字段，但需求文本明确要求"菜单里面的菜品需要有图片，**价格**，计量单位信息，并且可以**修改价格**"，故本设计 menu_items **包含 price 字段**（以需求文本为准）。

### 4.4 订单（order form）与订单明细（order_items）

订单包含：

| 字段 | 说明 |
|---|---|
| 员工姓名 | 下单人快照 |
| 联系电话 | 快照（送餐用） |
| 工位信息 | 快照（送餐用） |
| 用餐日期 | 订的是哪天的午餐（决定"每天一单"的唯一性） |
| 下单时间 | |
| 订单状态 | 有效/已取消 |
| 点餐表（明细） | 菜名、单位、分量、单价、合计价格（= 分量 × 单价） |
| 总计价格 | 明细合计之和 |

### 4.5 总括订单（blanket order）

无需单独存储，为**查询汇总**：某天所有有效订单按菜名 + 单位汇总分量。

### 4.6 报表数据

均为查询统计结果，无新增实体：

- **月度销售统计总报表**：统计年月 + 菜品统计信息（菜名、单位、分量、单价、合计价格）+ 总计价格。
- **员工月度菜品统计表**（个人月度消费统计）：员工姓名、联系电话、统计月份、菜名/单位/分量/单价/合计、合计金额、操作员、操作时间。
- **员工月度订单汇总表**：某员工某月全部订单（每天一张）及明细。

## 5. 业务规则

### 5.1 订餐时间窗口（核心规则）

系统有两个可配置时间点：**订餐截止时间**（默认 09:00）与**配餐开始时间**（默认 11:30）。

以当天日期为 D，当前时刻为 now：

| 条件 | 可订餐？ | 订单的用餐日期 |
|---|---|---|
| now 时间 < 订餐截止时间 | ✓ | D（当天午餐） |
| now 时间 ≥ 配餐开始时间 | ✓ | D + 1（第二天午餐） |
| 其他（截止后、配餐开始前） | ✗ | — |

即：D 天午餐的订餐窗口为「D-1 天配餐开始时间 ～ D 天订餐截止时间」，与需求描述"配餐开始时间后，用户即可进行第二天的订餐，直到第二天订餐截止时间"一致。

- 判定一律在**服务端**进行（前端时间不可信）。
- 配餐开始时间必须晚于订餐截止时间（保存配置时校验）。

### 5.2 订单唯一性

每个员工每个**用餐日期**最多一张**有效**订单，数据库以 `(user_id, meal_date)` 唯一约束保证；经理删除（取消）订单后，员工可重新下单。

### 5.3 快照机制（数据独立性）

需求要求"删除或修改食谱中的菜式信息**不能影响**已有的点餐单、菜单或订餐记录"，设计采用**三层快照**：

```
recipe（菜品库）──选菜快照──▶ menu_items（菜单项）──下单快照──▶ order_items（订单明细）
```

- 菜单创建时，菜品信息（名称/图片/单位/分类/价格）从 recipe **复制**到 menu_items，此后与 recipe 相互独立；menu_items 价格可单独修改。
- 下单时，菜品信息从 menu_items **复制**到 order_items，此后订单与菜单相互独立。
- recipe 可任意增删改，不影响任何历史菜单与订单。

### 5.4 菜单生命周期

```
[创建] → [使用中] →（创建/启用新菜单，旧菜单自动转历史）→ [历史] →（可重新启用）→ [使用中]
```

- 同一时刻**有且仅有一份**使用中的菜单。
- 历史菜单留存，可复用（重新启用）。
- 切换菜单不影响已提交订单（快照保证）。

### 5.5 统计口径

- 订单归属月份按**用餐日期**（meal_date）计算，而非下单时间。
- 月度销售总报表菜品汇总：按 菜名 + 单位 分组；分量 = 合计分量；合计价格 = 该菜品所有明细金额之和；单价显示 = 合计价格 ÷ 合计分量（加权平均价）。
- 已取消订单不参与统计。
